# Customer impersonation

Select the optional `customer-impersonation` add-on and choose `administration.host=admin` or `administration.host=merchant-center`. The selected host installs its impersonation screen and backend, together with the storefront's impersonation notice. Standalone Admin serves `/impersonation` through the web backend at `/api/auth/impersonation`; Merchant Center serves `/:projectKey/:entryPoint/impersonation` through the API app at `/impersonation`. Merchant Center requires commercetools; standalone Admin also works with Shopify or CMS-only applications. The previous `customer-impersonation-admin` selection remains a standalone Admin compatibility alias. It works with either auth provider and does not require company registration, fulfillment, custom checkout, or commerce. The standalone Admin recipe installs its package-owned screen. Merchant Center is a self-contained app recipe with app-owned UI; both hosts reuse shared commands, clients, schemas and native adapters. Admin and storefront permission manifests stay separate.

Shared screen templates live with the auth contract and materialize into the selected auth provider package; no Commerce Core dependency is introduced.

The screen looks up an identity by exact customer email or authentication user ID in the customer identity application. This first slice does not search commerce companies or choose a company for the customer. The storefront's existing authorized company switcher and buyer-context checks continue to apply. Finding an auth identity does not grant it a commerce membership.

## Setup

Configure customer `CLERK_SECRET_KEY` or `WORKOS_API_KEY` in the web application's server environment. Configure its independent **Admin** verifier using `ADMIN_CLERK_*` or `ADMIN_WORKOS_*`. The Admin application never receives the customer application's secret. Set `IMPERSONATION_API_URL=https://<web-origin>/api/auth/impersonation` in the Admin environment. Grant `impersonation.read` and `impersonation.start` through that isolated Admin application's normal permission configuration. Pages, actions and the backend enforce permissions independently; navigation does not authorize anything.

Clerk issues a one-use actor-token destination with a ten-minute ticket lifetime and a thirty-minute resulting session limit. The signed actor includes the verified staff subject, its authority (`admin` for the included verifier), staff session ID when available, and reason. Use the returned native URL so Clerk handles replacing any existing customer session and consuming its ticket. No passwords are collected. Launch URLs contain bearer credentials: responses use `private, no-store` and `no-referrer`; do not persist or log those URLs. No local token or credential collection is created.

WorkOS needs `WORKOS_ENVIRONMENT_ID` as well as the customer API key. Enable native impersonation in that environment and configure the AuthKit application's Initiate login URI to its sign-in route so PKCE/state initialize correctly. The returned link opens the native WorkOS dialog; the operator needs a permitted WorkOS team account and supplies the actual reason there. Preparing this link does not start or record a customer session. The native impersonator might differ from the Admin user requesting the link; audit records report WorkOS's actual impersonator and reason. We do not claim those staff identities are linked.

## Actor and audit ownership

Shared `AuthSession` and `VerifiedAccessToken` preserve provider-verified impersonation facts in `actor`. Native actor claims remain available for attribution. Clerk supplies the actor subject; WorkOS supplies the staff email and reason where available. Email is not promoted into an immutable staff ID. Customer identity, memberships and permissions remain the customer's. No Admin grants are copied into its authority. Malformed actor data is rejected instead of silently turning an assisted session into self-service.

`ImpersonationAudit.list({ userId, cursor })` is the audit-source Effect capability. The selected auth provider's default adapter reads native session records for that exact customer, filters out ordinary sessions, and preserves pagination even when a page contains no impersonation records. Coverage is explicit: Clerk returns native session history, while WorkOS's list API returns active sessions only. WorkOS responses declare `coverage: active` and include a native dashboard audit link; ended, revoked and expired sessions require that dashboard's records or a configured archive. A WorkOS team login is required to view the dashboard. Session IDs, actual actor, reason, native status and timestamps are returned. A requested WorkOS dashboard link is never represented as a started session. Native session retention and the availability of history after deletion are determined by the identity provider; this feature does not promise a permanent archive or record every launch attempt, ticket issuance, customer action, or Order placement.

Projects needing an independent archive can supply their own `ImpersonationAudit` Layer. `ImpersonationRecorder.observe({ actor, sessionId, userId })` is the separate recording capability. Compose `recordedAuthSessionAdapterLayer` over the installed `AuthSessionAdapter` and a recorder Layer, and provide that resulting adapter to the application runtime. It records only impersonated-session observations. Observations do not establish the session's creation time; an archive can retrieve native session metadata when needed. Recorders must deduplicate by provider and native session ID, own retention/erasure, and keep credentials out of records. A selected recorder's failure stops an assisted request through that composed session adapter rather than silently bypassing recording. No recorder is required when using the provider's native records.

For example, the composition shape is `recordedAuthSessionAdapterLayer.pipe(Layer.provide(Layer.mergeAll(authSessionAdapterLayer, archiveRecorderLayer)))`. `archiveRecorderLayer` is the project's implementation of `ImpersonationRecorder`. Its history adapter supplies `ImpersonationAudit`; it can be substituted in the HTTP service Layer without changing the screen or contract.

The native recorder is the provider's own session storage, not an application no-op that claims to have saved data. An unconsumed ticket need not appear in session history. A lost issuance response does not prove that no ticket exists. End impersonation through the displayed storefront sign-out route; this uses the installed logout composition, including Shopify cleanup when selected, while the independent Admin login stays separate.

## HTTP and other hosts

- `GET /users?query=<exact-email-or-auth-user-id>` requires `impersonation.read`.
- `GET /sessions?userId=<auth-user-id>&cursor=<opaque-continuation>` requires `impersonation.read`.
- `POST /launch` with `{ userId, reason }` requires `impersonation.start` and returns `{ mode, url }`, where mode is `direct` or `providerDashboard`.

All paths are relative to `IMPERSONATION_API_URL` and require a verified staff bearer token. A launch resolves the target against the customer provider before issuance. Submitted actor fields do not establish staff identity. The default verifier rejects nested impersonation as staff authority. Responses omit credentials and provider diagnostics on failure.

`ImpersonationAuthentication` lets each staff host provide its own verified actor and permissions. Reuse `auth-impersonation` and the selected native `auth-<provider>-impersonation` recipe; mount `makeImpersonationHttpHandler` with the chosen authentication Layer and audit Layer. The default Admin route is owned by `auth-impersonation-api` and is not needed to call the underlying commands. A Merchant Center adapter must verify the signed exchange JWT, exact project/audience/issuer, and the installed application's exact permission before mapping it to the feature permission. The commercetools Merchant Center recipe installs that verifier in the API app and its app-owned UI in `apps/ct-admin`. It mounts these shared operations at `/impersonation`, uses separate View/Manage impersonation grants, and does not install the standalone Admin verifier. The route runtime caches native service layers and JWKS clients, while verifying each request’s credentials independently. See `apps/ct-admin/README.md` for setup.

## Verification and limits

Source tests cover permission checks, independent staff attribution, invalid/foreign native records, pagination, recorder failures and HTTP seams. Composition tests cover both auth providers with CMS-only, B2C and B2B apps, with and without the add-on. The feature does not configure external providers or start impersonation during composition.

Live checks remain required for external Merchant Center/Admin subjects in Clerk actor claims, ticket consumption in the deployed sign-in UI, native WorkOS configuration, logout and Shopify's OIDC/hosted-checkout handoff. Existing ordinary-customer SSO verification does not prove impersonated sessions carry through Shopify or preserve upstream actor data in Shopify Orders.
