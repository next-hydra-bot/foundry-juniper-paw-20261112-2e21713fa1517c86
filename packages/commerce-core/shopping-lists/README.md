# Shopping lists

On every PDP, the add-on installs a request-time Wish List control and an Add to another list picker, including creation of a list with the selected Variant and quantity. The Wish List heart follows the same Variant selection as the purchase controls, including option changes and variant deep links. Saved state is read for the verified buyer; it is never put into the public catalog cache. Anonymous shoppers get a sign-in link. Failed reads do not present an unchecked heart as if absence had been confirmed. Failed writes leave the last confirmed state visible.

`purpose` distinguishes ordinary shopping lists from the default Favorites list, independently of a translated or user-edited name. Favorites lookup is `ShoppingLists.get(principal, { storeKey, purpose: "favorites" })`; ID-based reads, updates and deletion retain opaque IDs and revisions. There is one Favorites list per verified site user and Store, additionally scoped to the selected Business Unit in B2B. Postgres enforces that with a partial unique index; commercetools uses a readable, project-unique native list key derived in its adapter. `setFavorite` expresses saved/not-saved intent, so saving twice does not increase quantity. It retries only confirmed creation/revision conflicts, at most twice; an unconfirmed write is never replayed automatically. Ordinary AddItem actions still increment quantities for repeat-purchase lists.

Stock subscriptions, stock thresholds and notification delivery are separate future behavior. Saving a list or variant does not subscribe anyone to notifications. Reordering into a Cart is also separate from saving list contents.

The add-on also installs `/account/shopping-lists` and `/account/shopping-lists/[id]`, with an account-navigation link. These signed-in pages create, rename and delete lists, update or remove saved lines, and manage ordinary shopping lists through rename/delete dialogs. Wish List shows saved Products and removal only; saving Products happens on PDPs. B2B supports own/other/all filters through the same permissions as the service. The Store comes from the current locale; submitted Store and company fields only guard stale forms and never establish access. All writes retain the last read revision. Errors remain visible, with a refresh action for conflicts or an unconfirmed write.

Saved rows resolve their opaque Variant IDs through `ProductDiscovery.findVariantCards`, displaying current Product names, selected option labels, images and Variant deep links. Both provider adapters interpret their own Variant identities; list storage keeps only the opaque reference and requested quantity. Missing Products remain visible and removable, and catalog failures are distinguished from unavailable Products. Add Products through the existing PDP controls. The list page does not contain catalog browsing or a product picker. Prices and add-to-cart orchestration are outside this list-management screen. UI copy is currently English in each installed locale, ready for translation through the normal message catalogs. HTTP shopping-list endpoints are not included.

For the Shopify demonstrations, refresh the selected workspace after enabling `commerce-shopping-lists`, run `pnpm --filter @repo/db postgres:up` from that workspace, set its server-only `DATABASE_URL`, and run `pnpm --filter @repo/db migrate`. Then sign in and open `/account/shopping-lists`. B2C list pages and PDP controls use the verified site session directly; they do not need a Shopify customer session or trigger a Shopify account handoff. Company buyers need the applicable `company.shoppingLists.*` grants in their selected Business Unit; membership alone is insufficient.

The transport-neutral public failure contract and safe projection live in `shopping-lists/public-errors.ts`. Web Action envelopes, request-context failure handling, translations and navigation stay under `shopping-lists/web`. Shopping-list mutations use the app-owned `Actions` binding. The web buyer resolver supplies the verified site identity and locale-derived Store; the B2B recipe replaces it with selected-company context resolution. Cart and catalog request services are composed independently.

The optional `commerce-shopping-lists` add-on installs one authorized `ShoppingLists` service in the storefront's application runtime. Its recipes select native commercetools Shopping Lists or the provider-neutral Postgres adapter for Shopify, then compose the B2C or B2B authorization Layer over that implementation. Select an explicit B2C/B2B purchasing recipe. Screens and HTTP endpoints call the same service directly.

Shopify B2C lists require site authentication and Postgres. Shopify Customer Accounts and Plus are not prerequisites for this application-owned feature. Company lists additionally require verified membership in the selected Business Unit.

Lists retain an explicit Store, localized name/description, opaque revision and opaque line identities. Customer lists belong to the verified site user (`authUserId`). Business Unit lists preserve both the selected Business Unit and their associated site user, allowing own/other permissions. Business Unit membership alone does not grant shopping-list actions. Prices are not stored; product display and cart additions must use current buyer-context catalog/cart capabilities.

Call `ShoppingLists` from `@repo/commerce-core/services/shopping-lists`, passing a verified `ShoppingListBuyer` and explicit Store in every operation. Authentication resolves that buyer at the entry boundary; the service does not read `CommerceContext` or capture a current shopper. Recipes select `@repo/commerce-b2c/shopping-lists/layer` or `@repo/commerce-b2b/shopping-lists/layer`. Each Layer captures its underlying implementation; B2B additionally captures the permission adapter and checks the acting user and selected Business Unit on each call. The application runtime exposes the decorated service, preserving its other capabilities. Storage Layers are composition inputs, not alternative application entry points. Pagination is newest-created first, with a keyset cursor and no offset scans. `get` returns None for missing/out-of-scope IDs. Mutations require the revision read by the caller and fail with `conflict` when stale. Reads and writes are combined in one service.

`AddItem` increments an existing matching variant quantity. `SetQuantity` and `RemoveItem` identify a saved line. New item drafts require only an exact opaque `VariantId` and positive integer quantity; the adapter supplies saved line identity and time. Names and descriptions are maps of language tags to text. `SetName`/`SetDescription` change one language, preserving the others. A null description value removes that language. No automatic translation is performed.

The native adapter requires `view_customers`, `view_shopping_lists` and `manage_shopping_lists`. It resolves the native Customer by the verified site user ID in `Customer.externalId`; the native ID remains inside the adapter. B2B requests use the acting Associate and selected Business Unit endpoints, so native My/Others permissions also apply. Provision those permissions on the native Associate Roles. Application permission definitions remain in Commerce B2B and are contributed only to the storefront manifest by the add-on; Admin has no list grants. List creation associates the acting Customer. The first slice manages exact saved variants and product lines; text lines, per-line custom fields, anonymous lists and ownership reassignment are not exposed. The native 250-product-line limit returns `limitExceeded`. Native retention follows the Project shopping-list configuration; configure it deliberately. Provider integration audit fields are not represented as auth-user identity.

The SQL recipe installs only when selected (Shopify selects it through this add-on). Set server-only `DATABASE_URL` and optionally `DATABASE_POOL_SIZE`, then run:

```sh
pnpm --filter @repo/db migrate
```

Tables, codecs, migrations and generation snapshots belong to Commerce Core. The shared `db` package owns the pool, Drizzle dependencies and migration execution. To generate future SQL from canonical source:

```sh
pnpm --filter @repo/db generate \
  --schemas-directory ../commerce-core/shopping-lists/postgres \
  --name describe-change commerce-shopping-lists
```

Add generated SQL/snapshots and their shared execution target to the SQL recipe. Runtime never creates tables or runs migrations. Postgres mutations use one transaction and a conditional revision update; line changes roll back with the header. Test with `TEST_DATABASE_URL` against an isolated schema. No commerce credentials or recovery records are stored in these tables.
